# 요구사항·데이터·엣지케이스

## 원문을 수용 기준으로 바꾸기

[요구사항 틀](../templates/requirements.md)을 이용해 R-ID, 원문 파일/위치, 사용자/상황, 필수 동작, 거부/실패 동작, 완료 조건, 확인 방법을 연결한다. “최적”, “안전”, “빠르게” 같은 표현은 원문에 있는 목표·제약·기대 결과로 구체화한다. 임의 기준을 확정 사실로 추가하지 않는다.

문서 간 충돌은 양쪽 원문과 결과에 미치는 영향을 적고 최신 명시적 우선순위를 확인한다. 동작을 바꾸는 질문만 요청한다. 답이 없을 때 적용한 가정은 눈에 띄게 표시하고 관련 R/E-ID에 연결한다.

## 데이터 엣지케이스를 검토하는 순서

1. **자료 목록:** 파일/시트, 스키마, 단위, 식별자, 참조 관계, 날짜·버전을 기록한다. 원본은 보존한다.
2. **검사 규칙:** 지문과 자료 설명에서 필수값·허용 범위·중복 정책·관계·업무 제약을 추출한다.
3. **가능한 전수 실행:** 기존 도구나 작은 스크립트로 모든 레코드를 읽고 규칙별 오류를 집계한다. 임의 표본만 보고 “문제 없음”이라고 하지 않는다.
4. **처리량 대조:** 입력 수, 읽은 수, 유효/오류 수, 관계 연결 전후 수를 확인한다. 조용히 누락/중복된 행이 없는지 본다.
5. **최소 사례:** 오류별 대표 행/키와 실제 문제를 남긴다. 원본 전체와 민감 값을 보고서에 복사하지 않는다.
6. **정책 결정:** 데이터 오류, 업무상 결과 없음, 실행/탐색 실패를 구분하고 각각의 사용자 안내와 상태 변화를 결정한다.

전수 처리가 환경/크기로 불가능하면 검사 범위·표본 선택·확인하지 못한 범위를 적는다. 모델이 자료를 읽고 요약한 것은 전수 실행 검사를 대체하지 않는다.

## 실제 데이터에 없어도 확인할 반례

| 분류 | 도출할 사례 |
|---|---|
| 존재/형식 | 빈 파일·빈 배열·필수값 누락·잘못된 타입·예상 밖 필드 |
| 식별/관계 | 중복 키·없는 참조·서로 모순되는 관계·같은 값의 다른 표현 |
| 경계 | 최소/최대 바로 미만·같음·초과, 0/음수, 날짜·단위 경계 |
| 업무 규칙 | 규칙을 각각 위반하는 최소 입력, 여러 규칙이 동시에 걸리는 입력 |
| 결과/상태 | 결과 없음·동률·부분 성공·중복 실행·실패 후 재시도 |
| 규모/접근 | 큰 입력, 허용되지 않은 요청, 민감 값 노출 가능성(해당 시) |

모든 분류를 무조건 구현하지 않는다. 현재 기능에 관련된 위험을 고르고 이유를 적는다. 정상 샘플과 반례 각각에 구체적인 기대 결과가 있어야 한다.

## 예외 정책

[엣지케이스 틀](../templates/edge-cases.md)에 E-ID, R-ID, 발견/합성 구분, 입력·발생 조건, 기대 동작, 정책 근거, 구현 경계, T/C-ID를 적는다.

- **차단:** 필수 불변식이나 적용 불가 조건 위반이면 변경 전에 거부하고 이유를 반환한다.
- **보류:** 판단 자료가 부족하면 임의 값을 만들지 않고 확인이 필요한 상태로 둔다.
- **경고/부분처리:** 지문이 허용한 경우에만 처리 범위와 빠진 항목을 명확히 반환한다.
- **정규화:** 명세가 허용하는 공백·형식 정리만 수행하고 의미를 바꾸는 보정을 숨기지 않는다.
- **실행 실패:** 무효 입력과 구분해 상태/오류를 반환한다. 이전 유효 상태가 부분 덮어써지지 않도록 한다.

## 메인 AI의 분석 지시 양식

메인 AI가 직접 분석하거나 독립 분석 작업자에게 전달할 때 사용하는 내부 양식이다. 사용자가 단계마다 입력할 프롬프트가 아니다.

```text
원문 조건과 데이터 설명을 근거로 R-ID별 경계/반례를 도출해라.
실제 데이터에서 발견한 오류와 합성 테스트 사례를 구분해라.
전수 검사가 가능하면 기존 도구/작은 스크립트로 처리 건수·오류·참조를 대조해라.
각 사례는 입력 조건, 기대 동작, 차단/경고/보류 등 정책, 근거,
구현 위치와 사용자/AI 확인 방법으로 연결해라.
지문에 없는 정책을 조용히 추가하거나 오류 행을 버리지 마라.
```
