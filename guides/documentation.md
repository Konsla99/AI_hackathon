# 기능 설명·핵심 주석·기록 규칙

## 작성 시점과 담당

설계 시 분석 문서를, 구현 전 검증표 초안을, 기능 구현과 함께 기능 README와 핵심 주석을 작성한다. 검증 후 실제 결과를 채우고 수정 시 설명도 갱신한다. 기능 작업자가 코드와 README를 같이 소유하고 메인은 연결 경로·계약·내용 일치를 확인한다.

기존 제출 문서가 같은 목적을 담당하면 그곳에 내용을 넣고 링크한다. 문서 작성이 구현과 분리된 마지막 장시간 작업이 되지 않게 한다.

## 기능 폴더 README

[기능 README 틀](../templates/feature-README.md)에서 다음을 채운다.

1. 어떤 사용자/업무 문제를 해결하며 어떤 R/E-ID와 연결되는가?
2. 주요 파일·클래스·함수의 책임과 외부에 공개하는 입력/출력 계약.
3. 동작 순서와 주요 알고리즘/업무 규칙: 선택 이유, 제약, 종료/실패, 최적성·성능 한계.
4. 대표 소형 입력 하나의 중간 과정과 기대 결과.
5. 예외처리·보안 경계·상태 보존과 코드 위치.
6. 실행/확인 방법, 관련 T/C-ID, 실제 확인 상태와 미확인.
7. 다른 모듈과의 연결 및 확장 시 주의점(필요할 때만).

클래스명/함수명은 실제 코드에서 확인하고 문서의 알고리즘·예외 동작을 구현과 대조한다. 단순 기능에는 짧게 작성하되 주요 기능 설명을 생략하지 않는다. 소스 파일마다 별도 md를 만들 필요는 없다.

## 사용자에게 도움이 되는 코드 주석

주석은 동작의 이유, 불변식, 처리 순서가 중요한 이유, 단위/경계, 실패 정책을 설명한다. 핵심 로직과 공개 경계에 언어의 docstring/JSDoc/XML 주석 등 관례를 사용한다.

```text
# 예시 형식이며 실제 정책은 과제 원문에서 결정한다.
# R-04/E-02: 유효성 검사에 실패하면 저장을 시작하지 않는다.
# 부분 저장 후 오류가 나면 이전 상태가 깨지므로, 검사를 모두 통과한 값만 넘긴다.
검증된_값 = 입력_검사(원본)
저장(검증된_값)
```

명백한 대입/반복문을 줄마다 설명하지 않는다. 문서에 비밀값·개인정보를 넣지 않는다. “안전함”, “최적임”처럼 검증 근거 없는 표현을 주석에 쓰지 않는다.

## 기록 간 연결

R-ID → E-ID → 모듈 계약/구현 → T/C-ID → 발견 결함 D-ID → 수정/재확인으로 연결한다. 각 문서에 전체 내용을 복사하는 대신 ID와 실제 경로를 링크한다.

사용자 테스트는 기대 결과와 실제 관찰을 구분한다. AI 검토에는 코드 검토만인지 실제 명령을 실행했는지 표시한다. 과제 후 본인 설명을 준비할 때도 본인이 판단/확인한 사실만 남긴다.

## 프로젝트 README

필수 환경/설치·실행·검사 명령, 실제 포트/경로, 안전한 테스트 자료 준비법, 분석/검증/기능 문서 링크와 알려진 한계를 간단히 적는다. 준비키트 사용법이나 키트를 만들던 대화는 실제 결과물 README에 복사하지 않는다.
