# 사용자 UI 확인과 AI 코드 검토

## 구현 전 준비

요구/예외 표에서 최소 수용 기준을 뽑아 [사용자 테스트 시트](../templates/user-test-sheet.md)와 [AI 검토표](../templates/ai-review.md)를 먼저 만든다. 지문·실제 데이터로 기대값을 정하고 구현 결과를 보고 기대값을 거꾸로 맞추지 않는다.

| 담당 | 최소 확인 |
|---|---|
| 사용자 | 주요 정상 흐름, 중요한 오류/거부/빈 결과, 결과 표시, 상태 보존을 UI에서 직접 확인 |
| AI | 요구 누락·과해석, 실제 코드 연결, 입력/예외, 알고리즘/계산, 보안, 문서/주석 일치 |
| AI의 빠른 실행 | 기존 빌드/타입 검사, 핵심 함수·요청의 작은 정상/실패 입력, 데이터 검사 집계 |
| 메인 통합 | 모듈 계약과 전체 흐름 연결, 제출/실행 경로 |

UI만으로 권한·계산·데이터 무결성을 확정하지 않는다. 해당 위험은 서버/업무 경계의 코드 검토와 필요한 작은 실행 확인을 붙인다. 실행하지 못하면 코드 검토만으로 표시한다.

## 사용자 시트의 최소 단위

T-ID별 R/E-ID, 준비/안전한 입력, 번호가 있는 조작 순서, 눈으로 판정할 수 있는 기대 결과, 실제 결과, 상태를 적는다. 기능별로 정상 경로와 위험이 큰 실패 경로부터 선정한다. 전 기능 수십 가지 조합을 무조건 생성하지 않는다.

사용자가 보고할 때 T-ID와 관찰한 값/현상만 전달해도 AI가 관련 코드와 E-ID를 찾을 수 있게 한다. AI가 사용자 확인 결과를 대신 추측해 채우지 않는다.

## 동시 검증 절차

1. 작성자를 완료/중단시키고 메인이 코드를 통합한다.
2. 커밋 또는 관련 파일 변경 상태, 데이터/설정 버전, 시작 명령과 실행 시각을 기록한다. 서버가 실제 그 버전을 쓰는지도 확인한다.
3. 사용자에게 시트를 전달하고 UI를 직접 조작하도록 한다.
4. AI는 같은 버전에서 읽기 중심으로 검토한다. 테스트 상태를 바꾸는 명령·공유 DB 변경·서버 재시작은 동시에 하지 않는다.
5. 발견 결함을 D-ID로 모으고 영향·재현·코드 위치를 기록한다.
6. 수정 시 사용자에게 해당 버전 테스트 종료/중단을 알리고, 수정 후 새 버전에서 영향 T/C-ID만 재확인한다.

AI 검토용 명령이 사용자 환경에 영향을 준다면 별도 안전한 입력/격리 환경을 쓰거나 사용자 확인 종료 후 실행한다.

## 검증 종류와 상태

- **실행 확인:** 명령/입력·기대/실제·종료 결과가 있다.
- **코드 검토만:** 실제 파일/함수를 읽어 확인했지만 실행하지 않았다.
- **사용자 확인 완료:** 사용자가 해당 버전에서 실제 관찰을 보고했다.
- **미실행/확인 대기:** 절차는 준비됐지만 수행되지 않았다.
- **차단/실패:** 원인과 영향, 재개 조건이 기록돼 있다.

코드 검토에서 문제가 안 보인다고 사용자 테스트 통과로 바꾸지 않는다. 새 코드가 들어오면 과거 버전의 통과 표시를 그대로 승계하지 말고 영향 항목을 확인한다.

## 결함 수정과 범위

D-ID에 심각도, R/E/T/C-ID, 재현 입력, 기대/실제, 원인·수정 파일, 새 버전·재확인을 연결한다. 데이터 손상·핵심 필수 실패·보안 경계를 우선하고 스타일·선택 기능은 뒤로 둔다. 완료는 수정한 사실과 재확인한 사실을 구분한다.

## 시간 제한

기존의 빠른 검사와 핵심 전체 흐름을 우선한다. 같은 파일이 바뀌지 않았는데 전체 검사·리뷰를 반복하지 않는다. 대형 UI 자동화/전수 조합/벤치마크 환경을 새로 구축하지 않는다. 지문이 요구한 검사와 실제 결함의 재확인은 수행하고, 환경 미지원은 명확히 적는다.

시험의 UI 조작은 사용자가 허용된 Browser에서 수행한다. 코드 검사와 UI 자동화를 혼동하지 말고 실제 시험 도구/규칙을 따른다.
