# 기능별 코드와 목적별 문서 구조

## 배치 기준

기존 프로젝트의 모듈·라우팅·빌드 관례를 먼저 확인한다. 새 프로젝트 또는 기존 구조가 허용할 때 아래 예시를 출발점으로 삼는다. 프레임워크가 요구하는 루트 파일은 정상 위치에 둔다.

```text
src/
├─ features/
│  └─ <기능>/
│     ├─ domain/          # 업무 객체·규칙·순수 계산 (필요 시)
│     ├─ application/     # 업무 시나리오·조율 (필요 시)
│     ├─ adapters/        # 파일·DB·외부 입출력 (필요 시)
│     ├─ ui/              # 해당 기능 화면/상태 (UI 과제일 때)
│     └─ README.md        # 실제 구현과 연결된 기능 설명
└─ shared/               # 둘 이상 기능이 실제 공유하는 안정된 코드

docs/
├─ analysis/
│  ├─ requirements.md
│  ├─ edge-cases.md
│  └─ design.md
└─ verification/
   ├─ user-test-sheet.md
   └─ ai-review.md

README.md                # 실행·환경·실제 문서 경로
프로젝트 설정 파일들
```

작은 기능은 domain/application 등의 하위 폴더 없이 몇 개의 응집된 파일과 README로 시작한다. 복잡도나 파일 소유권 문제를 해결할 때 계층을 늘린다. 프레임워크가 UI/API를 app/pages/controllers 등으로 나누면 그 관례를 유지하고 기능의 규칙·설명·계약을 연결한다.

## 기능·공통·계층 판단

- 함께 변경되고 하나의 업무 결과를 만드는 코드는 기능 폴더에 모은다.
- 업무 규칙은 UI에서 분리하되, 실제로 필요하지 않은 저장소/서비스 계층을 자동 생성하지 않는다.
- shared는 실제 공통 타입·순수 도구·기반 컴포넌트에 한정한다. 향후 재사용을 예상해 모든 기능 코드를 옮기지 않는다.
- 기능 간 호출은 공개 인터페이스를 통하고 다른 기능의 내부 상태에 직접 접근하지 않는다.
- 데이터/스크립트/검사 파일은 기존 관례에 맞는 별도 위치에 두고 원본 자료와 생성물을 구분한다.
- 임시 로그·설명·메모를 루트에 계속 생성하지 않는다. 생성물은 목적별 기존 경로와 Git 제외 정책을 따른다.

## 문서의 소유 위치

| 내용 | 기본 위치 |
|---|---|
| 요구·완료 기준 | docs/analysis/requirements.md |
| 데이터 발견·합성 반례·예외 정책 | docs/analysis/edge-cases.md |
| 모듈/OOP·계약·알고리즘 선택·분담 | docs/analysis/design.md |
| 기능 동작·구체 로직·예외·검증법 | 해당 기능/README.md |
| 사용자 UI 기대·실제 결과 | docs/verification/user-test-sheet.md |
| AI 코드 검토·결함·수정·재확인 | docs/verification/ai-review.md |
| 실행법·문서 탐색 | 프로젝트 README.md |

큰 기능의 알고리즘 설명이 길어지면 해당 기능/docs/algorithm.md 등으로 세분화하고 기능 README에 링크한다. 다른 문서에 같은 내용을 복제하지 않는다. 필수 제출 문서가 이미 있으면 기본 경로보다 그 양식을 우선하고 README에 실제 위치를 안내한다.

## 새 파일 생성 전 판단

어느 기능/목적에 속하는가? 기존 파일에 넣는 편이 자연스러운가? 누가 수정하는가? 공개 계약인가 내부 구현인가? 이 네 질문에 답하고 경로를 고른다. 루트 생성이 꼭 필요하면 프레임워크/설정상의 이유를 명확히 한다.
