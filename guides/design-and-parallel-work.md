# 설계·OOP·병렬 작업 하달

## 설계에서 결정할 것

[설계 틀](../templates/design.md)에 요구/엣지케이스를 입력으로 다음만 결정한다.

- 기능별 책임과 경계, 상태를 소유하는 객체/서비스, 공통 코드의 범위.
- 입력/출력 데이터 구조, 함수/API 계약, 오류 상태와 호출 순서.
- 알고리즘의 목표·하드 제약·선택 이유·종료 조건·유효성/최적성 한계.
- UI의 주요 흐름과 로딩/빈 값/성공/오류 상태, 관련 보안 경계.
- 파일 배치, 의존 방향, 병렬 가능 작업과 순차 통합 지점.
- 각 기능 README·핵심 주석·사용자/AI 검증 항목의 담당.

문서만 정교하게 만들지 말고 작은 입력으로 핵심 판단과 인터페이스가 맞는지 확인한다. 3~5개 실행 단위로 계획하고 계약 변경 시 영향 모듈을 표시한다.

## OOP 설계 원칙

- 한 클래스/객체는 응집된 업무 책임을 맡고, 자신의 상태·불변식을 보호한다.
- 외부에서 내부 상태를 임의 변경하지 못하게 하고 의미 있는 메서드로 업무 동작을 제공한다.
- UI, 파일/DB 접근, 핵심 업무 판단의 책임을 분리해 같은 로직을 여러 화면에서 복제하지 않는다.
- 의존성이 있는 저장소/외부 서비스는 명시적으로 전달한다. 인터페이스는 실제 교체/검증 경계가 필요할 때 둔다.
- 상속보다 합성을 우선하고, 한 번 쓰는 단순 계산·변환은 순수 함수로 둘 수 있다.
- 기존 언어/프레임워크의 관용 구조를 따른다. OOP를 이유로 모든 파일에 클래스나 추상 계층을 만들지 않는다.

## 관련 보안 경계

현재 기능에 해당하는 경계만 설계·C-ID에 연결한다. 별도 인증 체계나 보안 보고서를 자동 추가하지 않는다.

- 입력은 서버/업무 경계에서 형식·길이·범위·관계를 검사하고 화면 검증만 신뢰하지 않는다.
- 접근 제어가 필요하면 신뢰 가능한 요청 주체에서 권한을 얻고 각 요청의 대상·동작을 검사한다. 요청 본문의 역할 값을 권한 근거로 쓰지 않는다.
- DB 질의는 매개변수 바인딩을 사용하고, 사용자 입력을 명령 문자열에 직접 붙이지 않는다. UI 출력은 해당 문맥에 맞는 안전한 렌더링을 사용한다.
- 파일 입력이 있으면 허용 경로·형식·크기를 제한한다. 실패/부분 처리 시 상태를 보존하고 내부 오류·비밀값을 응답/로그에 노출하지 않는다.
- 위험한 변경은 관련 허용/거부 사례와 상태 보존을 실제로 확인한다. 코드 검토만 했다면 실행 확인과 구분해 기록한다.

## 병렬 가능성 판단

다음 조건이 맞으면 실제 도구 한도 안에서 독립 기능을 동시에 구현한다.

1. 각 작업의 입력/출력·오류 계약이 고정돼 있다.
2. 수정 파일이 겹치지 않으며 기능 README도 해당 작성자가 소유한다.
3. 다른 작업의 미완성 구현을 기다리지 않고 계약과 안전한 합성 입력으로 진행할 수 있다.
4. 메인이 통합·검사할 시간이 남아 있다.

선행 계약/모델이 계속 바뀌거나 대부분 같은 파일을 고치면 순차 처리 또는 읽기 전용 검토로 줄인다. 세션 수·에이전트 수는 실제 지원 한도를 확인하고 자동으로 특정 숫자를 가정하지 않는다.

## 세션과 작업자의 배치

분석부터 구현·통합까지 메인 담당을 유지한다. 독립 검토자는 원문과 PRD의 누락/모순을 확인하고, 이후 같은 역할로 코드·요구·예외를 대조할 수 있다. 검토자는 발견 근거와 수정 제안을 반환하고 메인과 같은 문서를 동시에 수정하지 않는다.

| 시점 | 추가 배정할 가치가 있는 작업 | 조건 |
|---|---|---|
| 요구 분석 | 데이터 전수검사·참조/집계 대조 | 자료가 크거나 여러 파일 관계가 복잡해 메인 분석과 분리할 이익이 있음 |
| 요구/설계 확정 전 | 독립 누락·과해석·반례 검토 | 원문·자료·PRD 경로를 제공하고 읽기 중심으로 수행 |
| 구현 | 기능별 구현과 해당 README | 계약·독점 파일·통합 경로가 정해져 있음 |
| 사용자 테스트 중 | 동일 버전의 코드·문서 검토 | 관련 코드·자료·서버 상태를 바꾸지 않음 |

환경 세팅이나 설명 문서 작성만을 위한 상설 세션은 기본으로 두지 않는다. 환경 문제 조사나 복잡한 알고리즘의 독립 검산이 실제로 생겼을 때 좁은 작업으로 추가한다. 구현자는 자기 기능 문서를 함께 작성한다.

사용자가 새 세션을 열어 인계할 때와 메인이 서브에이전트를 배정할 때를 구분한다. 같은 도구로 위임 가능하면 메인이 관리하는 한시적 작업자를 우선하고, 별도 세션을 사용하면 문서 경로·확정 결정·미해결 사항·소유 파일로 인계한다. 역할 수를 채우기보다 작업 단계에 맞춰 인원을 바꾼다.

## 역할·소유권

| 담당 | 소유 |
|---|---|
| 메인/통합 | 요구·설계 결정, 공통 타입, 진입점/라우터, 의존성/lockfile, Git, 최종 연결 |
| 기능 작업자 | 독점 기능 폴더의 구현·핵심 주석·README와 해당 빠른 확인 |
| 독립 검토자 | 요구/엣지/계산/보안/설명 대조. 지정 시 읽기 전용 |
| 사용자 | 테스트 시트에 따른 UI 실제 관찰과 본인 이해 확인 |

같은 작업트리는 Git index와 파일을 공유한다. 작업자가 동시에 add/commit/checkout하지 않는다. 파일 독점이 어려우면 이미 지원되는 worktree를 검토하되 브랜치 통합 비용이 더 크면 사용하지 않는다.

## 메인 AI가 작성·전달하는 작업 하달문

아래는 메인 AI가 내부 작업 지시에 사용하는 양식이다. 메인 AI는 요구사항·설계·실제 경로에서 값을 채우고 사용 가능한 에이전트 도구의 작업 인자로 직접 전달한다. 사용자가 빈칸을 채우거나 작업자에게 복사해 전달하는 절차를 전제로 하지 않는다.

메인 AI는 작업 시작/완료/차단을 추적하고, 누락·충돌을 확인해 통합한다. 에이전트 도구를 지원하지 않으면 같은 작업을 순차 수행한다. 결과를 바꾸는 업무 결정이 필요할 때만 사용자에게 질문한다.

```text
역할/기능: <기능>.
작업 루트: <실제 경로>.
요구·예외: <R/E-ID와 원문 경로>.
설계/계약: <design.md의 계약 위치, 정확한 입력·출력·오류>.
수정 허용: <독점 파일/폴더>. 기능 README도 함께 작성해라.
공통 타입·진입점·의존성·Git은 메인이 소유한다. 변경이 필요하면 제안만 반환해라.
다른 작업자의 변경을 덮어쓰거나 되돌리지 마라.
완료 조건: <동작·주석·README>.
빠른 확인: <기존 명령/소형 입력/기대 결과>.
마감: <시각>. 계약 불일치/막힘은 바로 원인과 필요한 결정을 알려라.
반환: 변경 파일, 실제 확인과 미확인, 계약 변경 제안, 통합 방법, 설명할 핵심 로직.
```

## 통합 순서

메인은 공통 계약을 준비한 뒤 기능 경계를 연결한 작은 전체 흐름부터 실행한다. 작업자가 기능을 반환하면 실제 diff·계약·빠른 검사 결과·README를 확인하고 연결한다. 독립 모듈이 통과해도 전체 UI/API 흐름 확인은 별도로 한다.

사용자 확인용 버전을 고정하기 전에 모든 작성 작업을 완료/중단하고 통합한다. 계약이 바뀌면 영향 모듈과 문서·T/C-ID를 함께 갱신한다.

## 작업별 모델 선택

실제 제공되는 모델 중 요구 충돌·알고리즘·보안·통합에는 판단 품질을, 계약이 고정된 구현에는 수정·검증까지 포함한 완료 시간을 기준으로 메인 AI가 배정한다. 문서 형식 정리에는 빠른 모델을 사용할 수 있으나 실제 코드와 대조한다. 도구가 모델 선택을 지원하지 않으면 현재 모델로 진행한다. 모델을 바꾸는 것만으로 독립 검증이 되는 것은 아니다.

## 스킬 호출·적용 기준

기본 작업 순서와 병렬 조율은 AGENTS/workflow가 담당한다. 스킬은 그 안의 구체적인 문제를 해결할 때 선택한다. 아래 이름은 후보이며 실제 설치된 이름·버전과 SKILL 원문을 먼저 확인한다.

| 시점·문제 | 후보 | 넘길 입력과 기대 결과 |
|---|---|---|
| 모듈 책임·공개 계약을 설계하기 어려움 | Matt Pocock `codebase-design` | 관련 R/E-ID와 현재 구조 → 작은 인터페이스 뒤에 책임을 모은 모듈 설계. 폴더/코드를 자동 생성하는 스킬로 오해하지 않음 |
| 독립 작업을 동시에 배정할 수 있음 | Superpowers `dispatching-parallel-agents` | 작업별 범위·계약·독점 파일·기대 결과 → 병렬 하달·결과 대조·통합. 스킬이 없어도 위 하달문과 제공 에이전트 도구로 조율 가능 |
| 실제 재현되는 버그 | Superpowers `systematic-debugging` | 재현 명령/입력·로그·관련 코드 → 원인 근거·최소 수정·같은 경로 재확인 |
| 최종 완료 주장을 점검할 때 | Superpowers `verification-before-completion` | 완료 기준·현재 버전·검사 명령과 결과 → 주장/실제 근거/미확인 대조 |

메인 AI는 자동 호출이 허용된 등록 스킬 중 적용할 것을 선택하고 SKILL을 읽은 뒤 사용한다. 명시 호출이 필요하면 현재 UI의 스킬 선택기나 Codex CLI의 `/skills`·`$`에서 실제 등록 이름을 선택한다. `@superpowers`처럼 전체 묶음을 지정하는 것만으로 아래 생략 범위가 적용된다고 가정하지 않는다.

호출 시에는 다음과 같이 대상과 범위를 구체적으로 준다. 이는 메인 AI가 채우는 내부 지시 예시다.

```text
현재 등록된 <실제 스킬 이름>의 SKILL을 읽고 <구체 문제>에 적용해라.
입력: <R/E-ID, 설계/소스 경로, 재현 명령 또는 실제 로그>.
결과: <계약 제안/원인과 수정/검증 근거>를 해당 기존 문서에 갱신해라.
이미 끝난 분석·승인을 반복하지 말고, 중복 문서나 작업별 다중 리뷰를 추가하지 마라.
빠른 기존 검사와 필요한 영향 범위 확인은 유지해라.
원본 스킬과 이 범위가 맞지 않으면 전체 스킬 실행 대신 해당 문제의 기본 작업 절차를 수행하고 그렇게 기록해라.
```

### 전체 방법론을 선택할 때의 차이

- 설치된 Superpowers `subagent-driven-development`는 구현 작업별 리뷰와 최종 리뷰를 포함하고 병렬 구현을 금지하는 버전일 수 있다. 현재 SKILL을 읽고 확인한다. 이를 기본 병렬 구현 엔진으로 자동 호출하지 않는다.
- Matt Pocock `implement-spec` 원문은 spec·의존관계 티켓·이슈 트래커, 작업별 worktree/TDD와 최종 코드 리뷰를 전제로 한다. 이 전체 흐름을 선택하려면 준비·통합 비용을 포함해 판단한다. PRD 파일 하나만 전달해 같은 결과가 나온다고 가정하지 않는다.
- Matt Pocock `grilling`은 질문 라운드와 사용자 확인을 요구한다. 지문에 답이 있는 사실을 다시 묻거나 시험 시작마다 전체 인터뷰를 자동 실행하지 않는다.
- Matt Pocock `ask-matt`, `implement-spec`, `handoff`처럼 원문에서 사용자 호출용으로 선언된 스킬은 메인이 자동 선택할 수 있는 것으로 전제하지 않는다. 인계는 기존 handoff 템플릿으로도 수행할 수 있다.

전체 스킬의 필수 단계를 생략했다면 원본 방법론을 완료했다고 쓰지 않는다. 선택한 절차와 실제 확인을 기록한다. 같은 단계에 두 플러그인의 전체 흐름을 겹쳐 적용하지 않는다.
